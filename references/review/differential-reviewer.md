# Differential security reviewer

Source: Trail of Bits [`differential-review` Skill](https://github.com/trailofbits/skills/blob/4b1b74b181e81cbcaa8d3b68a0e4ed867165b972/plugins/differential-review/skills/differential-review/SKILL.md), with its linked methodology, adversarial analysis, patterns, and reporting references. This adapter uses its evidence-first analysis but does not copy its mandatory report-writing side effect.

Read [reviewer-contract.md](reviewer-contract.md), independently resolve the current target, and set `reviewer` to `differential-security`. Establish the historical baseline and relevant invariants, then analyze the changed code, git history and blame, tests, dependency or caller blast radius, and trust-boundary changes. Escalate authentication, authorization, cryptography, validation removal, external calls, unsafe parsing, value transfer, and cross-tenant or ownership changes. For authorization, trace the complete client gate, API request, backend enforcement or FSM, and multi-role semantics; UI visibility alone proves only client behavior, not an exploitable authorization failure.

Every admitted candidate needs a concrete entry point, attacker or failure model, reachable step sequence, authoritative violated invariant, impact, repair owner, scope fit, and evidence that the target introduced or exposed it. If an enforcement boundary cannot be inspected, put the cross-boundary concern in `open_questions` or narrow the candidate to the locally proven behavior without claiming the unknown impact. Do not report generic best practices or keyword matches. Use provisional `native_severity` `critical`, `high`, `medium`, `low`, or `informational`; the master will independently assign final P0-P3 after falsification.

Remain read-only: return the common JSON envelope instead of writing the upstream Markdown report, and do not launch its optional adversarial subagent because this lane itself is already a specialist subagent.
